## 🎯 Mission Briefing

You are an Enterprise Splunk Detection & Ingestion Engineer at **FinCorp Global**.  
The SOC Threat Response team needs to correlate security incidents across Linux servers and Windows Domain Controllers.  
However:
1. An administrator attempted to build an eventtype with a transform pipe: `search = "error" | dedup host`, triggering an error in `splunkd.log`.
2. Windows security events (`EventCode=4625`) and Linux SSH failures (`"Failed password"`) are isolated in disparate indexes, requiring cumbersome multi-index queries.
3. Automated alert triggers looking for `tag=authentication tag=failure` are failing because tags were attached to the wrong configuration stanzas.

Your mission is to eliminate invalid eventtype pipe commands, unify authentication failure patterns under `eventtypes.conf`, deploy certified CIM tags in `tags.conf`, and capture all 4 flags!

## 🧭 Task 1: Eliminating the Illegal Pipe in `eventtypes.conf`

An administrator deployed this stanza:
```ini
# /opt/splunk/etc/apps/fincorp_soc/local/eventtypes.conf
[web_server_crashes]
search = sourcetype=nginx:access status>=500 | stats count by clientip
```
Splunk Web displays an error alert:
`Invalid search in eventtypes.conf: piping commands are not permitted in eventtype definitions.`

### Question 1.1
Explain why piping commands are forbidden in `eventtypes.conf`, and provide the clean, corrected stanza.

<details>
<summary>💡 Hint</summary>
Eventtypes are pure event classifiers that run during the initial event discovery phase. Remove <code>| stats ...</code>.
</details>

<details>
<summary>🔑 Solution & Flag</summary>
<strong>Explanation:</strong> Eventtypes are evaluated event-by-event to assign the <code>eventtype</code> metadata badge. Transforming commands like <code>stats</code>, <code>dedup</code>, or <code>sort</code> aggregate multiple events and cannot be evaluated as an event-level boolean filter.<br/>
<strong>Corrected Stanza:</strong><br/>
<pre><code>[web_server_crashes]
search = sourcetype=nginx:access status>=500</code></pre>
<strong>Flag 1:</strong> <code>THM{EVENTTYPE_PIPE_SYNTAX_VIOLATION_ELIMINATED}</code>
</details>

## 🧭 Task 2: Building Cross-Platform Unified Eventtype `auth_failures`

The SOC team wants a single eventtype named `fincorp_auth_failure` that triggers on:
1. Linux authentication failures (`sourcetype=linux:secure` and phrase `"Failed password"`)
2. Windows authentication failures (`sourcetype=XmlWinEventLog:Security` and `EventCode=4625`)

### Question 2.1
Write the complete `eventtypes.conf` stanza combining these two conditions using boolean logic.

<details>
<summary>💡 Hint</summary>
Use parentheses and the <code>OR</code> operator between the two sourcetype conditions.
</details>

<details>
<summary>🔑 Solution & Flag</summary>
<strong>eventtypes.conf:</strong><br/>
<pre><code>[fincorp_auth_failure]
search = (sourcetype=linux:secure "Failed password") OR (sourcetype=XmlWinEventLog:Security EventCode=4625)</code></pre>
<strong>Flag 2:</strong> <code>THM{CROSS_PLATFORM_AUTH_FAILURE_UNIFIED}</code>
</details>

## 🧭 Task 3: Mapping Multi-Tag Taxonomies in `tags.conf`

For Splunk Enterprise Security to identify these authentication failures in the `Authentication` data model, the eventtype `fincorp_auth_failure` must carry two distinct tags:
- `authentication`
- `failure`

### Question 3.1
Write the exact stanza in `tags.conf` to attach both tags to `eventtype=fincorp_auth_failure`.

<details>
<summary>💡 Hint</summary>
Stanza header must be <code>[eventtype=fincorp_auth_failure]</code>, followed by each tag set to <code>enabled</code>.
</details>

<details>
<summary>🔑 Solution & Flag</summary>
<strong>tags.conf:</strong><br/>
<pre><code>[eventtype=fincorp_auth_failure]
authentication = enabled
failure = enabled</code></pre>
<strong>Flag 3:</strong> <code>THM{MULTI_TAG_CIM_TAXONOMY_DEPLOYED}</code>
</details>

## 🧭 Task 4: Field-Specific Tagging via `tag::<field>`

The SOC team needs to tag specific high-risk executive laptops as `vip_asset`:
- `host=exec-laptop-01`
- `host=exec-laptop-02`

### Question 4.1
Configure `tags.conf` to tag both hosts as `vip_asset`, and write the SPL query that uses `tag::host` to search only events generated by these VIP machines.

<details>
<summary>💡 Hint</summary>
Create stanzas <code>[host=exec-laptop-01]</code> and <code>[host=exec-laptop-02]</code> with <code>vip_asset = enabled</code>. Search with <code>tag::host=vip_asset</code>.
</details>

<details>
<summary>🔑 Solution & Flag</summary>
<strong>tags.conf:</strong><br/>
<pre><code>[host=exec-laptop-01]
vip_asset = enabled

[host=exec-laptop-02]
vip_asset = enabled</code></pre>
<strong>SPL Search Query:</strong><br/>
<pre><code>tag::host=vip_asset</code></pre>
<strong>Flag 4:</strong> <code>THM{FIELD_SPECIFIC_TAG_HOST_SCOPED}</code>
</details>
